# Dynamic Comparator Layout Task

## Objective

Create an IHP SG13G2 layout for the `DIFF_COMPARATOR` dynamic differential
comparator. Preserve the topology, device parameters, explicit well and
substrate connections, and eight-port interface in the authoritative materials.
The submitted GDS must pass the physical checks, fit the functional outline, and
meet the clocked decision requirements after candidate-derived RC extraction.

### Optimization objective

Maximize the declared quality score within the solve budget while satisfying all physical and necessary functional requirements. The first passing DRC, LVS and required electrical checks establish a feasible baseline. Continue improving the scored metrics from that baseline; a passing check or `task_success = true` does not mean that the quality objectives have been achieved.

## Inputs and Interface

In addition to this description, the solver receives the following declared materials. The runtime `/protocol/task.json` also supplies structured constraints and the evaluation plan.

| Input | Purpose |
|---|---|
| [materials/circuit.cdl](materials/circuit.cdl) | Authoritative LVS netlist for `DIFF_COMPARATOR` |
| [materials/circuit.spice](materials/circuit.spice) | Pre-layout simulator netlist |
| [materials/testbench.spice](materials/testbench.spice) | Clock stimulus and public measurement expressions |

Use one distinct external conductor for each ordered port. Internal nodes must
not be exposed as ports.

| Port | Function |
|---|---|
| `vdd` | Positive supply |
| `gnd` | Ground and substrate reference |
| `V+`, `V-` | Differential input pair |
| `clk` | Dynamic latch clock |
| `out-`, `out+` | Complementary decision outputs |
| `vbias` | Bias input |

The extraction port order is `vdd gnd V+ V- clk out- out+ vbias`.

## Operating Conditions

The supplied deck evaluates the pre-layout and candidate-derived netlists with
the same model and stimulus definitions.

| Parameter | Setting |
|---|---|
| Process corner | `mos_tt`, `res_typ` |
| Temperature | 27 °C |
| Supply | `VDD = 1.2 V` |
| Input reference and bias | `V- = vbias = 0.6 V` |
| Differential input | `V+ − V- = −5, −3, +3, +5 mV`, tested separately |
| Clock | 100 MHz, 1.2 V swing, 500 ps rise and fall, 5 ns high time |
| Output load | 50 fF on each output |
| Transient analysis | 100 ns duration, 10 ps maximum time step |
| Measurements | Skip the first two cycles and evaluate the next eight cycles |

The testbench excludes power consumed by the external clock, input, and bias
drivers from the reported supply-power measurement.

## Physical Requirements

Submit a readable GDSII file with a nonempty `DIFF_COMPARATOR` top cell. The file
must be at most 10 MiB (10,485,760 bytes) and must contain the complete hierarchy
needed by the target cell.

The evaluator runs the pinned SG13G2 main and additional maximal DRC rules in
deep mode, with density and antenna checks disabled and no waivers. LVS uses the
current `lvs-upstream.json` profile and strict named-port matching against
`materials/circuit.cdl`; port names are matched case-insensitively, while every
declared port must remain on its own conductor with the declared connectivity.

The functional outline is the recursive bounding box of polygons on the following SG13G2 datatype-0 layers, including child cells and every routing layer:

`1, 3, 5, 6, 7, 8, 10, 11, 13, 14, 19, 24, 26, 28, 29, 30, 31, 32, 33, 35, 36, 40, 44, 46, 49, 50, 51, 52, 53, 55, 58, 66, 67, 90, 101, 111, 125, 126, 128, 129, 133, 134, 139, 152`.

The maximum width is 45 µm and the maximum height is
45 µm, measured along the submitted X and Y axes.
Functional area is width multiplied by height. Text, annotation and filler
layers are excluded. The area score below uses this same functional footprint.

After the physical and geometry gates pass, Magic extracts distributed wire
resistance and layout capacitance from the submitted GDS. Device merging and
resistor-network simplification are disabled. The compact-device extraction
boundary represents MOS bodies at ideal model rails; explicit taps remain part
of physical LVS but are not emitted as extracted tap elements. Substrate sheet
and tap resistance as extracted quantities, body coupling, and noise are outside
the declared scope. The source and post-layout runs use the same nominal
stimuli and models; a finite-source-tap versus ideal-body calibration bounds this
extraction choice.

## Electrical Requirements and Scoring

Artifact, geometry, DRC, LVS and declared functional requirements must pass. Parasitic extraction is also mandatory: it must produce a complete, electrically consistent netlist usable by the required post-layout simulations. A completed candidate rejection scores zero; infrastructure errors do not establish candidate failure.

Physical checks and the declared functional bounds must pass. Quality scoring imposes no fixed degradation allowance. Each `source_*` job and its corresponding candidate extracted circuit use exactly the same testbench, model resources, parameters, loads and measurement windows. Independent source observations define the 100-point electrical baseline without depending on the submitted GDS; reports retain every paired result.

Let x be the post-layout measurement and b the source-circuit measurement under the same conditions:

- Ratio normalization: maximize with q = x/b and minimize with q = b/x. When a numerical scale s is declared, use (x+s)/(b+s) and its reciprocal, respectively. The scale handles zero values as a normalization floor; it is neither an allowed degradation nor an acceptance bound.
- Amplitude in dB: maximize with q = 10^((x-b)/20) and minimize with its reciprocal.
- Target normalization: q = 1/(1+abs(x-b)/s), where s is the declared physical scale. Signed or zero-valued operating points are not divided directly.

Use `layout` scoring. Each metric takes its worst paired quality q, and the total score is S = 100 * product(min(1, q_i) ** w_i), with area quality q_area = area_reference / candidate_functional_area. The weights below sum to 1; metric dimensions describe measurements and do not determine weights. Physical, extraction, or functional rejection scores zero; other missing or invalid measurements leave the score unknown, and zero-weight observations must also be valid. Matching source-circuit performance at the reference area scores 100 points; each metric is capped at quality 1, so scores cannot exceed 100. Weights express quality tradeoffs rather than hard bounds.

The measurements below use the supplied SPICE node and source names. `v(n)` is a node voltage; `i(V)` is current flowing into a voltage source, so delivered power uses a negative sign. `db(z)=20*log10(abs(z))`; `mag/abs` denote magnitude, and `cph` denotes continuous phase in radians. `find`, `when`, `from/to` and `rise/fall` follow the deck's interpolation, window and crossing conventions. SPICE suffixes p/n/u/m/meg/g mean pico/nano/micro/milli/mega/giga. Nested `avg`, `min`, `max`, `vecmin/vecmax` and `deriv` represent window averages, extrema and sampled derivatives. Measure each operating condition independently, pair it with the source result under that condition, and take the worst paired quality within each metric group.

| Metric | Definition / observation | Unit | Quality normalization | Functional range | Scale | Dimension |
| --- | --- | --- | --- | --- | --- | --- |
| `worst_delay` | Clock falling through 0.6 V to polarity-correct output difference reaching 1 V in cycles 2–9 (trigger delays 20–90 ns; target search starts 5.75 ns later). Every cycle and input condition is paired; the worst quality is scored. | s | minimize / ratio | 0 … +∞ | — | response |
| `decision_margin` | Minimum polarity*(V(OUTP)-V(OUTM)) in each 1 ns decision window, 28.75–29.75 ns through 98.75–99.75 ns; all eight cycles and four signed input conditions must pass. | V | functional check | 1.0 … +∞ | — | functional check |
| `supply_power` | Mean delivered VDD power, -V(VDD)*I(VDD), over 20–100 ns, independently for each signed input condition. | W | minimize / ratio | 0 … +∞ | 1e-12 | supply |

Area reference: **502.96 um2**. The expanded circuit has 24 device instances, a sum of device/contact envelopes 306.3377 um2, a one-sided envelope margin of 0.6 um, a routing allowance of 50%, and a total outer width/height allowance 1.2 um. Estimate = ceil(100 * (1.5 * envelope_sum + 2 * margin * sqrt(envelope_sum) + margin^2)) / 100. Here margin is the total allowance across both sides, and the envelope sum is displayed to four decimal places. MOS/passive envelopes use W/L (or resistor dimensions) and multiplicity, including explicit contacts and HBT emitter/contact envelopes. This is a frozen engineering estimate, not a process minimum or a proven achievable area.

The capability coefficient is **6**, independent of this task's reference-normalized score.

## Tools and Submission

Soft solve budget: **3 hours**.

The runtime environment and support resources are declared in
the `resources` field of `/protocol/task.json` and `/protocol/harness.json`; the working directory is
`/workspace`. KLayout performs artifact, DRC, LVS, and geometry checks; Magic
performs RC extraction; ngspice runs the supplied deck with the reviewed SG13G2
models. The evaluator provides the tool and PDK resources named by the case
toolchain.

For pre-layout simulation, use `materials/circuit.spice` as `dut.spice`
beside the supplied testbench and use the per-job values exposed in
`/protocol/task.json`. For the submitted layout, the evaluator supplies the
netlist produced by candidate-derived RC extraction. If the harness declares
`process-feedback`, use the full-plan check command
`python -I /protocol/process_check.py`; the final evaluation remains independent.

Write the result to `/workspace/output/final.gds`, run `python -I /protocol/submit.py` and wait for a submission receipt. Solver netlists, waveforms and measurements cannot replace independent evaluator inputs.

### Solve workflow

1. Read the declared circuit and materials, `/protocol/task.json` for paths, constraints and reviewed resources, and `/protocol/harness.json` for capabilities and helper commands. Task inputs under `/task` and resources under `/resources` are read-only; construct the layout in `/workspace` with the declared tools. With layout MCP, paths and commands refer to the remote EDA workspace. Create your own implementation with real devices, interconnect and pins, using your own tool loop without delegating to other agents; reference layouts and author code are not solver inputs.
2. Inspect `resources.external` before using external tools. Each command starts a fresh shell: when tool modules are declared, source `/usr/share/Modules/init/bash` and load the selected tool's modules; export its declared `tool_environment` settings in that same command. Repeat as needed and use batch or headless operation. Local manuals, command references, and release notes may be available within the declared EDA installation and PDK resource directories. Locate these resources through `/protocol/task.json` and consult the documentation for the installed tool version when diagnosing unfamiliar syntax or tool failures.
3. Generate an initial candidate and submit a snapshot early. When `process-feedback` is available, check the current GDS with layout MCP `check` or `python -I /protocol/process_check.py` before the final submission. This runs the final evaluator's complete plan and returns engineering diagnostics and candidate measurements, without scores or normalized quality factors. Checks have no count limit and consume the same wall-clock budget. Inspect the physical and functional results and all scored metrics; successful tool execution alone does not establish requirement satisfaction. Read paginated diagnostics with `report` when using MCP. Local exploratory checks do not replace this complete check.
4. Use the remaining time for measured improvements to the declared quality objectives. Identify the limiting scored metrics, make targeted layout changes, regenerate and check the candidate, and compare measurements with the previous candidate and the stated scoring targets and trade-offs. Preserve the best valid candidate and revert changes that worsen the overall objective. Repeat while time and useful improvements remain; passing validity checks alone is not a stopping condition.
5. Stop optimization when the budget expires, all declared quality objectives are achieved, or measured trials support convergence. If stopping early, explain the changes tried, the metric comparisons and the remaining limitations. Track remaining time through session status. At soft-budget expiry, finish or cancel already-started work and submit immediately; do not start another command, check or optimization round. If an MCP execution is running, use `poll` with its `execution_id` and the returned `next_offset` as `offset` until completion, or cancel it and wait for it to stop.
6. Finish or cancel outstanding work, restore your best candidate to the declared output path, and explicitly submit it before ending the session. With layout MCP `submit`, remove the `/workspace/` prefix from `output.path`; with the container interface, run `python -I /protocol/submit.py`. Wait for the receipt: only the last accepted snapshot is judged, and writing a file alone is not submission. Acceptance confirms delivery; the framework independently evaluates validity and quality after the session.
