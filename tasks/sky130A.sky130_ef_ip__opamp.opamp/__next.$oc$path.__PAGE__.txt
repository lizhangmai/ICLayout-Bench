4:T2490,<h1 id="problem-sky130-33-v-operational-amplifier-layout-task">SKY130 3.3 V Operational Amplifier Layout Task</h1>
<h2 id="problem-objective">Objective</h2>
<p>Implement <code>sky130_ef_ip__opamp</code> from the supplied transistor-level circuit, preserving topology, fixed device parameters, four-terminal body connections and the ordered interface. Submit a candidate GDS for electrical evaluation of its distributed RC extraction.</p>
<h3 id="problem-optimization-objective">Optimization objective</h3>
<p>Maximize the declared quality score within the solve budget while satisfying all physical and necessary functional requirements. The first passing DRC, LVS and required electrical checks establish a feasible baseline. Continue improving the scored metrics from that baseline; a passing check or <code>task_success = true</code> does not mean that the quality objectives have been achieved.</p>
<h2 id="problem-inputs-and-interface">Inputs and Interface</h2>
<p>Ordered ports are <code>vdd out ena vss inp inm</code>. Declared inputs include <code>problem.md</code>, <code>materials/circuit.spice</code> <code>materials/testbench.spice</code> and <code>materials/dynamics.spice</code>. The runtime provides models and process resources; reference layouts, author code and qualification evidence are maintainer-only materials.</p>
<h2 id="problem-operating-conditions">Operating Conditions</h2>
<p>Supply 3.3 V, enable 1.8 V, input common mode 1.65 V. Use output loads 0.1, 0.5, 1 pF and 100 Mohm resistance; the declared large-inductance/capacitance fixture closes DC feedback and breaks AC feedback. Measure low-frequency gain, unity-gain crossing, phase margin and supply power. 5 pF is outside this task's operating conditions. All electrical experiments use fixed TT models at 27 °C; delivered testbenches define interpolation, edges, loads, sweeps, observation times and power intervals.</p>
<p>Dynamic tests reuse the upstream CACE unity-feedback slew apparatus: drive the input from 0 to 3.3 V or back at 100 ns with 0.1 ns edges, and measure the output interval between 0.5 and 2.8 V. Repeat unloaded and with 0.1/1 pF loads. Stop at 10 us with a 2 ns maximum step. The measured interval is used directly rather than the upstream hard-coded 2 V slew numerator; the actual threshold separation is 2.3 V.</p>
<h2 id="problem-physical-requirements">Physical Requirements</h2>
<p>Submit a nonempty GDS no larger than 10485760 bytes, with top cell <code>sky130_ef_ip__opamp</code>. Functional geometry must fit within the 80 × 100 um envelope on the declared layer set. Pass complete Magic DRC without waivers and independent Netgen LVS checking named ports, models, dimensions, multiplicities and body/contact connections. After physical and geometric checks pass, extract the candidate's distributed interconnect resistance, capacitance and devices, then run every declared experiment.</p>
<h2 id="problem-electrical-requirements-and-scoring">Electrical Requirements and Scoring</h2>
<p>Preserve the existing physical, extraction, output-bias and stable phase-branch requirements. Every declared source and candidate measurement must be complete and finite. Dynamic crossing intervals must be nonnegative. No minimum score or fixed speed/power target is an acceptance cutoff.</p>
<p>Pair every electrical observation with the same-condition pre-layout circuit and take the worst quality per metric. Rising/falling intervals use q=2(b+s)/(b+x+2s), with s=1 ns. Existing loaded bandwidth normalization remains in the contract. Area quality is 1500 um2 divided by candidate functional area; this 30 by 50 um integration allocation is independent of the feasibility witness and permits other aspect ratios. The score is 100 times the product of min(1,q) raised to each weight. Invalid candidates score zero; incomplete measurements leave the result unknown.</p>

<h3 id="problem-solve-workflow">Solve workflow</h3>
<ol>
<li>Read the declared circuit and materials, <code>/protocol/task.json</code> for paths, constraints and reviewed resources, and <code>/protocol/harness.json</code> for capabilities and helper commands. Task inputs under <code>/task</code> and resources under <code>/resources</code> are read-only; construct the layout in <code>/workspace</code> with the declared tools. With layout MCP, paths and commands refer to the remote EDA workspace. Create your own implementation with real devices, interconnect and pins, using your own tool loop without delegating to other agents; reference layouts and author code are not solver inputs.</li>
<li>Inspect <code>resources.external</code> before using external tools. Each command starts a fresh shell: when tool modules are declared, source <code>/usr/share/Modules/init/bash</code> and load the selected tool's modules; export its declared <code>tool_environment</code> settings in that same command. Repeat as needed and use batch or headless operation. Local manuals, command references, and release notes may be available within the declared EDA installation and PDK resource directories. Locate these resources through <code>/protocol/task.json</code> and consult the documentation for the installed tool version when diagnosing unfamiliar syntax or tool failures.</li>
<li>Generate an initial candidate and submit a snapshot early. When <code>process-feedback</code> is available, check the current GDS with layout MCP <code>check</code> or <code>python -I /protocol/process_check.py</code> before the final submission. This runs the final evaluator's complete plan and returns engineering diagnostics and candidate measurements, without scores or normalized quality factors. Checks have no count limit and consume the same wall-clock budget. Inspect the physical and functional results and all scored metrics; successful tool execution alone does not establish requirement satisfaction. Read paginated diagnostics with <code>report</code> when using MCP. Local exploratory checks do not replace this complete check.</li>
<li>Use the remaining time for measured improvements to the declared quality objectives. Identify the limiting scored metrics, make targeted layout changes, regenerate and check the candidate, and compare measurements with the previous candidate and the stated scoring targets and trade-offs. Preserve the best valid candidate and revert changes that worsen the overall objective. Repeat while time and useful improvements remain; passing validity checks alone is not a stopping condition.</li>
<li>Stop optimization when the budget expires, all declared quality objectives are achieved, or measured trials support convergence. If stopping early, explain the changes tried, the metric comparisons and the remaining limitations. Track remaining time through session status. At soft-budget expiry, finish or cancel already-started work and submit immediately; do not start another command, check or optimization round. If an MCP execution is running, use <code>poll</code> with its <code>execution_id</code> and the returned <code>next_offset</code> as <code>offset</code> until completion, or cancel it and wait for it to stop.</li>
<li>Finish or cancel outstanding work, restore your best candidate to the declared output path, and explicitly submit it before ending the session. With layout MCP <code>submit</code>, remove the <code>/workspace/</code> prefix from <code>output.path</code>; with the container interface, run <code>python -I /protocol/submit.py</code>. Wait for the receipt: only the last accepted snapshot is judged, and writing a file alone is not submission. Acceptance confirms delivery; the framework independently evaluates validity and quality after the session.</li>
</ol>
